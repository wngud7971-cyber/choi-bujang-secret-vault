## 3. 값의 출처와 실제 조회 경로

조회 흐름은 브라우저 ‘내 PC 상태’ → 로컬 서버의 POST /api/pc-status/sample → on-client/src/pc-status.mjs → Node.js의 OS·파일 시스템 API → 학생 표시 함수다.

기록 복원은 GET /api/pc-status로 수행한다. 이 두 경로는 기존 보안 엔진의 연결 상태와 독립적이다. 응답의 보안 엔진 meta.mode가 disconnected 또는 demo여도 PC 자료는 data.kind=measured로 구분하며, PC 수집이 성공했다고 보안 엔진을 connected로 바꾸지 않는다.

| 지표 | 실제 조회·계산 | 단위·비교 시 주의 |
|---|---|---|
| CPU | node:os.cpus의 전체 논리 CPU 시간을 약 1초 간격으로 읽고 총 시간 대비 유휴 시간 차이로 계산 | %, 직전 변화는 %p. 작업 관리자의 갱신 시각·주파수 보정·집계 방식과 차이가 날 수 있음 |
| 메모리 | node:os.totalmem - node:os.freemem | 사용 GiB, 전체 GiB, 사용 %. 특정 Node 프로세스의 메모리가 아님 |
| C: 공간 | node:fs/promises.statfs의 블록 크기와 일반 사용자 가용 블록 수 | 남은 GiB, 전체 GiB, 남은 %. 작업 관리자의 디스크 활동률과는 다른 지표 |

1 GiB는 1,073,741,824 bytes다. CPU·메모리는 작업 관리자 ‘성능’에서, C: 남은 공간은 파일 탐색기의 C: 속성에서 가까운 시각·같은 단위로 비교한다. 숫자가 다르거나 일정하다는 사실만으로 예제값으로 판단하지 않고 위 조회 코드·측정 시각·집계 범위를 확인한다.

관리자 실행 요청, 외부 프로그램·패키지 설치, PowerShell 조회 명령, AI API 호출은 수집 코드에 없다. Node.js 기본 API로 읽고 실패 이유를 표시한다.

## 4. 로컬 기록

보관 위치는 on-client/.local/pc-status/history.jsonl 이다. .gitignore에 on-client/.local/을 추가했으며 서버의 정적 파일 목록에도 기록 파일을 등록하지 않았다. 이 경로를 HTTP로 요청하면 공개하지 않는다.

기록은 서버에서 직렬로 저장하고, 같은 5초 측정 주기의 중복 요청은 합쳐 다중 탭으로 기록이 중복되는 것을 줄인다. 주기는 측정 시작 시각을 기준으로 하며 서버가 알려주는 다음 측정 가능 시각에 화면 요청을 맞춘다. 조회할 때 24시간 밖의 기록을 제외하며, 이후 측정 저장 시 만료 기록을 파일에서도 정리한다. 앱이 꺼져 있으면 수집·파일 정리는 실행되지 않는다.

파일 손상·권한 문제·보관 위치 확인 실패는 ‘기록 보관 확인 불가’로 안내한다. 그 경우 현재 실측값과 기록 저장 성공을 구분하며, 기존 손상 파일을 덮어쓰지 않는다. 이번 기능은 기록 파일을 제출·외부 전송하지 않는다. 향후 별도 패키징에서도 이 실행 데이터를 제외해야 한다.

8. PowerShell에서 Ctrl+C로 종료하고 같은 명령으로 재실행한다. ‘내 PC 상태’로 들어가 24시간 이내 기록이 복원되는지 확인한다.
9. 오류가 나면 새 프로젝트를 만들거나 기록 파일을 지우지 말고 화면의 오류 문구를 확인한다. 과거 기록은 현재의 정상값으로 해석하지 않는다.
10. 상단 연결 오류의 ‘항목별 오류 상세 보기’를 펼쳐 원래 사유를 확인한다. ‘보호 현황’에서는 ‘연결 진단 도움정보’, ‘AI 계정 연결과 응답 점검’, ‘설치 패키지와 취약점 조회’를 펼치면 기존 버튼을 사용할 수 있다. ‘제공 기능 · 직접 구현 구분’ 안내도 펼쳐 볼 수 있다. 펼치기 자체가 조회·AI 요청·조치를 실행하지 않는다.

정상 결과는 새 실측값과 시각이 표시되고 재실행 후 기록이 복원되는 것이다. 거부 결과는 외부 출처의 측정 POST, 임의 파일 경로 입력, 기록 파일 직접 요청이 허용되지 않는 것이다. 실제 읽기 실패는 정상 숫자 대신 ‘확인 불가’와 이유가 나와야 한다.

자동 시험 재실행은 기존 프로젝트 최상위에서 다음을 사용한다.
