## 1. 확정한 앱의 방향

**내 서비스와 연결된 PC·네트워크를 보호하는 통합 방어 앱**을 목표로 한다.

우선 프로젝트 자체의 방어를 완성하고, 장기적으로 등록된 PC와 네트워크 장비에 방어 기능을 연결한다. 범용성을 유지하면서 계정 악용, 서비스 요청 폭주, 취약점 악용과 자료 유출처럼 실제로 대응할 위협을 구체적으로 정한다.

주제·핵심 기능·화면 구성·디자인 요소를 정할 때는 반드시 사용자에게 먼저 묻는다. 아래 핵심 방향과 구현 우선순위는 대화에서 승인받았다. 화면 틀, 디자인, 포장 방식, 세부 차단 정책과 연동 서비스는 아직 확정하지 않았다.

### 2.2 현재 실행과 기존 방어 코드 사이의 경계

현재 기본 실행의 흐름은 브라우저 → `on-client/src/server.mjs` → 엔진 조회/판정 메서드 → 학생 표시 함수다. 실제 SDP 설정이 없으면 `on-client/src/engine.mjs`는 미연결 상태를 사용한다. `--demo`는 별도 합성 응답이며 루트 방어 정책의 실제 실행 결과가 아니다.

루트의 `api/` 서버 API와 `src/decider.mjs`·`src/detect.mjs`·`src/ztna.mjs`·`xdr/`는 보존된 기존 구현이다. `on-client`를 시작하는 것만으로 이 코드 전체가 자동 실행되지는 않는다. SDP 설정을 지정하면 기존 host/adapter를 통해 서버에 조회할 수 있지만, 연결된 서버가 이 저장소의 판정기를 실제로 사용한다는 사실까지 자동 증명하지는 않는다. 기존 서버의 정책 배치·사건 전달·자원 접근 경로를 각각 대조해야 한다.

SDP 설정과 개인 자격은 담당자가 안내한 기존 발급 경로를 사용해야 한다. 앱의 AI 계정 연결이나 Workbench 설치만으로 이 SDP 연결이 준비된다고 가정하지 않는다. 비밀값을 채팅으로 받거나 가상 신원·공용 인증서로 실제 연결을 대신하지 않는다. 이번 문서 보완에서는 설정 파일·개인 자격을 검색하거나 연결 옵션·보안 설정을 바꾸지 않았다.

### 2.3 재사용을 위한 확인 순서

1. 보호 대상과 실제 서버가 무엇인지, 담당자가 제공한 SDP 연결 안내·설정이 있는지 확인한다. 세부 대상·정책·새 기능은 사용자와 결정한다.
2. 준비된 연결에서 본인 신원·앱·기록의 조회 경로와 범위를 확인한다. 원천 기록은 Windows 경고·오류 집계와 구분한다.
3. 연결된 서버가 기존 접근 판정·XDR 규칙을 사용하는 경로를 확인하고, 정상 허용·거부·추가 인증·제안·실제 효과를 분리해 확인한다. 아직 수행하지 않은 확인은 미확인으로 남긴다.
4. 기존 구현으로 충족되지 않는 API 요청 제한 등 추가 범위는 보호 경로·정책·완료 기준을 먼저 합의한다. 공격·침투·부하를 흉내 내는 시험이나 관리자 보안 설정 변경은 이번 보완에 포함하지 않는다.

## 3. 계정 악용·자료 유출·랜섬웨어의 관계

- **계정 악용**: 탈취하거나 부적절하게 부여받은 권한으로 자원에 접근하는 행위다.
- **자료 유출**: 보호할 자료가 승인되지 않은 경로 또는 대상으로 반출되는 피해다.
- **랜섬웨어**: 파일 암호화 등으로 사용을 막고 금전을 요구하는 공격이다. 자료 유출을 함께 수행하는 경우도 있다.

예를 들어 계정 탈취 → 내부 접근 → 자료 유출 → 파일 암호화·협박으로 이어질 수 있다. 자료를 빼내지 않고 파일만 암호화하는 공격도 있으므로, 계정·유출 방어만으로 랜섬웨어 대응이 완성됐다고 판단하지 않는다.

**이번 구현 우선순위는 계정 악용·자료 유출 방어다.** 기존 접근 판정과 반출 탐지 코드를 이어가면서 실제 거부·회수·차단을 검증하는 것을 우선한다. 랜섬웨어 대응은 이후 PC 보안 도구, 악성 실행 차단, 감염 기기 격리, 보호된 백업과 복구를 연결하며 확장한다. 구체적인 연동 범위는 사용자와 별도로 정한다.

참고: [CISA #StopRansomware Guide](https://www.cisa.gov/stopransomware/ransomware-guide).

## 6. 다시 실행하고 확인하는 방법

사용자 PowerShell에서는 `node`가 명령으로 인식되지 않았다. 아래의 이미 존재하는 실행 파일과 기존 앱 파일의 전체 경로로 실행했다. 이번 실행에는 별도 npm 의존성 설치가 필요하지 않았다. 이 명령은 현재 PC에서 확인한 경로이며, 다른 PC에서는 실제 Node.js 설치 경로를 확인해야 한다.

```powershell
& 'C:\Users\82109\.cache\codex-runtimes\codex-primary-runtime\dependencies\node\bin\node.exe' 'C:\Users\82109\Documents\ChatGPT\hackert0n\step22-main\on-client\src\server.mjs'
```

1. PowerShell에 위 한 줄을 입력한다. 이미 서버가 켜져 있으면 같은 명령을 중복 실행하지 않고 그 창을 유지한다.
2. `케셰브 연결 확인: http://127.0.0.1:5189` 메시지를 확인하고 브라우저에서 해당 주소를 연다.
3. ‘보호 현황’에서 ‘연결 없음’과 계정·기기·세션의 조회 실패 안내를 확인한다. 이번 기본 실행 조건에서 관측한 상태이며 실제 연결 성공으로 해석하지 않는다.
4. ‘도움정보’의 ‘도움정보 불러오기’를 누른다. engine의 `disconnected / ENGINE_NOT_CONNECTED`, AI의 `configured: false / authorized: false`를 확인한다. 시각과 요청 식별자는 매 실행마다 달라질 수 있다.
5. ‘업무 앱’·‘보안 기록’ 메뉴와 ‘다시 불러오기’는 추가 화면 확인에 사용할 수 있다. 이 버튼들을 사용자가 모두 조작했다고 기록하지 않으며, 기본 미연결 상태에서는 실제 목록·판정을 기대하지 않는다.
6. 종료는 서버를 실행한 PowerShell 창에서 Ctrl+C다. 다시 실행할 때는 위와 같은 명령을 사용한다.

예제 판정을 다시 확인하려면 실행 창에서 Ctrl+C로 기본 서버를 종료한 뒤 위 명령 끝에 `--demo`를 붙여 실행한다. 이 절차는 기본·예제 서버가 같은 포트를 동시에 사용하지 않게 한다. 예제 모드의 자료실 allow·저장소 deny는 앞선 HTTP 점검 결과이며, 사용자가 예제 화면의 버튼을 누른 것으로 기록하지 않는다. 기본 모드로 돌아오려면 예제 서버를 종료하고 위 원래 명령으로 다시 실행한다.
